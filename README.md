# 3D Engineering Volgograd

Сайт инженерной 3D-мастерской: Nuxt 4 / Vue 3 / TypeScript / Tailwind CSS, Django 5.2 LTS / DRF, PostgreSQL, Nginx и Gunicorn.

Фактически выполненные проверки и оставшиеся ограничения: [VERIFICATION.md](VERIFICATION.md).

Главный сценарий: администратор создаёт проект с фотографиями, выбирает «Опубликовано» — проект появляется на SSR-сайте при следующем открытии страницы, без сборки или перезапуска. Форма клиента сохраняет заявку и приватные вложения, возвращает уникальный номер и ставит уведомление в очередь.

## Быстрый запуск в Docker

Нужны Docker Engine/Desktop с Linux-контейнерами и современный Docker Compose (2.24+).

```sh
docker compose up --build -d
```

Команда запускает PostgreSQL, применяет миграции, создаёт начальный редактируемый каталог и явно помеченные демонстрационные данные, запускает API, обработчик уведомлений, Nuxt SSR и Nginx. В production создаётся только каталог, без демонстрационных проектов (`bootstrap_content`).

- Сайт: http://localhost:8080
- Админка: http://localhost:8080/admin/
- Healthcheck: http://localhost:8080/api/health/

Создайте администратора самостоятельно; общей учётной записи и пароля в исходниках нет:

```sh
docker compose exec backend python manage.py createsuperuser
```

Для изменения настроек скопируйте `.env.example` в `.env`. Локальный запуск работает и без этого файла. Данные сохраняются в именованных volumes `postgres_data`, `public_media`, `private_media`. Обычный `docker compose down` их сохраняет; флаг `-v` удаляет данные.

```sh
docker compose ps
docker compose logs -f backend frontend notifications nginx
docker compose down
```

## Что реализовано

- Главная, шесть страниц услуг, каталог и страницы материалов, контакты, политика и согласие.
- Портфолио с категориями, поиском и пагинацией; отдельная страница каждого опубликованного проекта.
- Django Admin: поля проекта и SEO, черновики, публикация, порядок, главная страница, обложка, inline-фотографии и стандартный множественный загрузчик.
- Миниатюры WebP, приём изображений JPEG/PNG/WebP/AVIF, подписи, lightbox, сравнение до/после.
- STL/GLB-просмотрщик с вращением, масштабом и сбросом вида. Код и файл модели загружаются только после нажатия на странице проекта.
- Приватные вложения заявок, статусы, внутренние заметки, предварительная и итоговая стоимость.
- Согласие с сохранением версии текста, CSRF, серверная валидация, honeypot, rate limit, идемпотентные повторные запросы.
- Очередь уведомлений email и опционального Telegram с повторными попытками.
- SSR, canonical, Open Graph, sitemap с актуальными опубликованными записями, robots, хлебные крошки и структурированные данные.
- Контакты, имя, логотип, тексты главной, услуги, материалы и юридические тексты хранятся в базе.
- Группы «Редактор контента» и «Менеджер заявок», TLS-конфигурация, резервное копирование, восстановление и тесты.

Никакие демонстрационные проекты не выдаются за реальные заказы: они отмечены в карточках и на странице проекта. Изображения демо — оригинальные технические иллюстрации. Реальные фотографии, контакты, реквизиты и подтверждённые характеристики должен добавить владелец.

## Работа в админке

1. Откройте «Проекты» → «Добавить».
2. Заполните название, slug, категорию, краткое описание и остальные поля задачи.
3. Загрузите обложку и выберите несколько файлов в «Добавить несколько фотографий».
4. У фотографий можно изменить подпись, порядок и роль «До»/«После» в inline-таблице.
5. Выберите статус «Опубликовано», при необходимости «На главной», сохраните.
6. Откройте `/projects/` или `/projects/<slug>` — новая работа доступна сразу.

В списке проектов доступны массовые действия «Опубликовать» и «Скрыть». Для услуги добавляйте FAQ в inline-таблице и связывайте материалы. Связанные проекты выбираются через поле «Услуги» в проекте.

«Настройки сайта» содержат название, контакты, главную страницу и юридические документы. Этапы и преимущества редактируются как JSON-массивы объектов `{"title": "...", "text": "..."}`. Поля адреса и карты оставляйте пустыми, если публичного адреса нет. Схема `LocalBusiness` появляется только при заполненном адресе; иначе используется `Organization`.

У пользователя Django должно быть `is_staff=true` и нужная группа. Сотрудник без права `leads.view_leadattachment` не может скачать вложения. Приватные файлы не имеют публичных URL; ссылка для сотрудника находится внутри заявки.

Публикация 3D-модели требует отдельного флага «Разрешить просмотр модели». Кнопки скачивания нет, но любой браузерный просмотр передаёт геометрию посетителю. Не используйте эту функцию для конфиденциальных исходников.

## Локально без Docker

Этот режим использует SQLite только для разработки. В Docker всегда используется PostgreSQL.

```sh
python -m venv .venv
# Windows:
.venv\Scripts\python -m pip install -r backend/requirements/lock.txt
# Linux/macOS:
.venv/bin/python -m pip install -r backend/requirements/lock.txt
```

Установите Node.js 22.22.3+ либо совместимую более новую LTS-версию. Затем:

```sh
cd frontend
npm ci
npm run build
```

В Windows из корня проекта:

```powershell
.\start-local.cmd
```

Сайт: http://127.0.0.1:3000, админка: http://127.0.0.1:8000/admin/. Скрипт запускает процессы скрыто; логи лежат в `.runtime/`. Обёртка разрешает выполнение PowerShell-скрипта только в своём процессе и не меняет системную execution policy. Она может использовать portable Node из `.tools/`, подготовленный при разработке. Эти каталоги и виртуальное окружение не входят в исходники.

```powershell
$env:DEBUG = 'true'
.\.venv\Scripts\python.exe backend/manage.py createsuperuser
.\stop-local.cmd
```

Для ручного запуска API: `DEBUG=true python backend/manage.py runserver 127.0.0.1:8000`. Для Nuxt: `npm run dev` в `frontend`. API проксируется через Nuxt, поэтому форма работает с CSRF на одном origin. Не выставляйте dev-серверы в публичную сеть.

## Уведомления

В `.env` задайте `EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend`, SMTP-параметры и `LEAD_NOTIFICATION_EMAIL`. По умолчанию используется консольный backend без адресата — заявка остаётся в админке и очередь ждёт конфигурации.

Telegram включается парой `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID`. В уведомления передаётся только номер заявки и ссылка на защищённую админку, без контактов и приложенных файлов.

Сервис `notifications` выполняет `process_notifications --loop`. Для разовой обработки:

```sh
docker compose exec backend python manage.py process_notifications
```

Сбой SMTP/Telegram не отменяет принятую заявку. Запись очереди показывает попытки и время следующей попытки. Доставка имеет семантику at-least-once: после сбоя между отправкой и фиксацией транзакции возможен повтор уведомления.

## Безопасность файлов

До 8 файлов, 20 МБ на файл, 50 МБ суммарно. Изображения проверяются декодером, для PDF/моделей проверяются формат и сигнатуры. Серверные имена — UUID.

ZIP не распаковывается. Проверяются пути, типы, количество записей, суммарный размер, коэффициент сжатия; вложенные архивы, ссылки и зашифрованные архивы отклоняются. Это не антивирус: сотрудники должны рассматривать неизвестные CAD/PDF-файлы как недоверенные. Вложения скачиваются принудительно как `application/octet-stream`.

Rate limit Django хранится в БД и работает между Gunicorn-процессами; Nginx дополнительно ограничивает запросы. Nginx перезаписывает `X-Real-IP`; порт backend не опубликован. При изменении схемы прокси сохраняйте эту границу доверия.

Публичный bucket S3 используется для опубликованного медиа, приватный — для исходных моделей и заявок; оба bucket должны запрещать анонимный листинг. Секреты хранятся только в окружении. При S3 отдельно организуйте резервирование и версионирование обоих bucket.

## Подготовка VPS

Production-деплой не выполнялся. Пример конфигурации:

1. Выберите инфраструктуру первичного хранения персональных данных в России согласно требованиям ТЗ; отдельно проверьте применимые правовые обязанности с юристом. Учитывайте также резервные копии, SMTP, S3/MinIO и доступ сотрудников.
2. Заполните реальные реквизиты, политику, отдельное согласие, сроки хранения и удаления. Исходные тексты — шаблоны. После проверки задайте версию согласия и «Юридические тексты проверены». При `DEBUG=false` форма не принимает обращения до этой отметки.
3. Установите уникальный `DJANGO_SECRET_KEY` (например, сгенерируйте через Python `secrets.token_urlsafe(64)`), сильный пароль PostgreSQL, `DEBUG=false`, `SEED_DEMO=false`, `SITE_URL=https://ваш-домен`, точные `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, `CORS_ALLOWED_ORIGINS`, `SECURE_SSL_REDIRECT=true`.
4. Уберите демонстрационные проекты из публикации, загрузите реальные фото. Добавьте контакты, подтвердите материал и технологию каждого проекта.
5. Получите сертификат для реального домена и положите `fullchain.pem` / `privkey.pem` в `infrastructure/certificates/` с ограниченными правами. Организуйте автоматическое продление и reload Nginx. Сертификаты не входят в Git.
6. Запускайте `docker compose -f docker-compose.yml -f docker-compose.production.yml up --build -d`. Оставленный локальный порт 8080 привязан к loopback; публичные порты 80/443 добавляет production override.
7. Проверьте `python manage.py check --deploy`, HTTPS, форму, уведомления, права сотрудников и восстановление резервной копии. Ограничьте админку через VPN/IP allowlist, если это подходит схеме работы; используйте отдельные учётные записи.

Не используйте локальные пароли из примера на VPS. Схема прокси не предполагает внешний CDN; при добавлении внешнего TLS-прокси настройте доверенные заголовки и доступ к origin.

## Резервные копии и восстановление

Скрипты требуют Python и запущенный Docker Compose. Они работают с локальными volumes, коротко останавливая принимающие запись сервисы для согласованной копии БД и файлов.

```sh
python scripts/backup.py
python scripts/restore.py backups/20261020T120000Z --confirm
```

Backup создаёт `database.dump`, `files.tar.gz` и SHA-256 manifest. Restore проверяет контрольные суммы и пути архива; затем заменяет базу и восстанавливает файлы. При ошибке восстановления приложение остаётся остановленным. Используйте только доверенные копии. Старые файлы, отсутствующие в восстановленной БД, не удаляются автоматически.

Для production используйте те же compose-файлы через переменную `COMPOSE_FILE` (Linux: `docker-compose.yml:docker-compose.production.yml`, Windows: разделитель `;`). Скрипты наследуют эту переменную.

Храните зашифрованную копию отдельно от VPS, ограничьте права, настройте расписание, срок хранения и контроль успешности. Для проверки сначала восстановите копию на отдельном стенде и проверьте: вход администратора, проекты и фото, заявку, скачивание приватного вложения.

## Проверки

```sh
docker compose exec backend python manage.py test apps.core
docker compose exec backend python manage.py makemigrations --check --dry-run
cd frontend
npm run typecheck
npm run build
```

17 backend-тестов покрывают API, публикацию через Django Admin, несколько фотографий и миниатюры, AVIF, CSRF, обязательное согласие и его версию, rate limit, идемпотентность, приватный доступ, ZIP, повтор уведомления, скрытые услуги/материалы, пагинацию и безопасный seed.

Для браузерных тестов запустите локальные API/Nuxt или Compose, затем в `frontend`:

```sh
npx playwright install chromium
npm run test:e2e
```

Базовые адреса задаются `E2E_BASE_URL` и `E2E_ADMIN_URL`. Для Compose оба адреса — `http://localhost:8080`. Полный сценарий админки требует `E2E_ADMIN_USER` и `E2E_ADMIN_PASSWORD`; создайте локальную тестовую учётную запись командой `python backend/manage.py prepare_e2e` с этими переменными и `DEBUG=true`. Без них админский браузерный тест пропускается; backend-тест этого сценария выполняется всегда.

Тесты создают только вымышленные записи с маркировкой E2E. Запускайте их на отдельном тестовом окружении. Для установленного Edge можно указать `E2E_CHANNEL=msedge`.

Для удаления только этих тестовых записей и учётных записей: `DEBUG=true python backend/manage.py cleanup_e2e`.

```sh
python scripts/verify_persistence.py
```

Последняя команда проверяет сохранение проектов, настроек и изображений после перезапуска контейнеров. Она требует работающего Docker. CI содержит backend-проверки на PostgreSQL и сборку Nuxt; запуск CI в этой сессии не выполнялся.

## Архитектура и расширение

```text
backend/
  config/                   Django settings, URLs, WSGI
  apps/core/                Общие валидаторы, API чтения, thumbnail, тесты, команды
  apps/portfolio/           Проекты, категории, фотографии
  apps/services/            Услуги и FAQ
  apps/materials/           Каталог материалов
  apps/site_settings/       Контент и настройки мастерской
  apps/leads/               Заявки, приватные файлы, уведомления
frontend/
  app/pages/                SSR-страницы Nuxt 4
  app/components/           Форма, галерея, сравнение, ленивый 3D-viewer
  app/composables/           Типизированное чтение API и SEO
  server/routes/            Локальный API-прокси, sitemap, robots
infrastructure/nginx/       HTTP/TLS и маршрутизация
scripts/                    Локальный запуск, backup/restore, проверка volumes
```

API чтения: `/api/settings/`, `/api/services/`, `/api/materials/`, `/api/categories/`, `/api/projects/`; детали — `/<slug>/`. Проекты принимают `category`, `material`, `service`, `search`, `featured=true`, `page`. Создание заявки: multipart `POST /api/leads/`, CSRF из `/api/csrf/`, UUID `idempotency_key`, `consent=true`, актуальная `consent_version` из настроек, вложения `files`.

Сущности заявки и её файлов разделены. Будущие анализы STL/OBJ/PLY, расчёт габаритов и стоимости, параметрический CAD и интеграцию QIDI можно добавить отдельным приложением с задачами, ссылающимися на `LeadAttachment`; исходные файлы останутся приватными. AI-функции, личный кабинет и автоматическая цена в первой версии не реализованы согласно ТЗ.

Технические ориентиры: [структура Nuxt](https://nuxt.com/docs/4.x/guide/directory-structure), [поддержка Django](https://www.djangoproject.com/download/), [Tailwind с Vite](https://tailwindcss.com/docs/installation/using-vite).
